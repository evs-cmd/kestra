# 3. Plugins are acquired just in time, with completion from a schema bundle

## Context

The plugin catalog grew from about 600 to more than 1,300 plugins in a year, and the image with every plugin bundled
passed 2.6 GB. Its size grows with every plugin, so no per-JAR optimisation can offset it, and every user pulls and
hosts plugins they never run. But a new user still needs the editor to know every plugin, and a first flow to run
without editing a Dockerfile or restarting anything.

Source: [Plugin Auto-Install & Schema Bundle](../architecture/PLUGIN_AUTO_DOWNLOAD.md).

## Decision

Split what the editor needs from what execution needs:

- **Completion from a schema bundle.** Release CI generates `plugins-schema.json` from the full plugin catalog and
  embeds it in the Kestra JAR. The API merges it into the local schema, so the editor completes every catalog
  plugin, installed or not, with no JAR and no network access.
- **Download on save.** When a flow is saved, the plugin JARs for the types it references and that aren't installed
  are downloaded.
- **On by default only where it fits.** Auto-install defaults to on only for the OSS edition with local-filesystem
  storage, the local evaluation case. It stays off by default for distributed OSS deployments and for the Enterprise
  Edition, where plugin installation is a governed admin operation. An explicit
  `kestra.plugins.auto-install.enabled` always overrides the default.
- **Three images.** A full image with every plugin (offline and air-gapped use), a slim image with the core engine
  and auto-install on, and a no-plugins image with auto-install off.

## Consequences

- A user's footprint is the core engine plus the plugins they use, an order of magnitude smaller in practice.
- The full catalog stays discoverable in the editor, even on a slim install.
- A build without the release CI step (a plain Gradle build, or running from source) has no embedded bundle, so
  catalog completion is inactive there unless a bundle is pointed to with `kestra.plugins.schema-bundle-path`.
- Saving a flow can fetch JARs over the network, which is why it's off by default outside local OSS evaluation.
- Release CI needs a two-pass build, because the bundle can only be generated by the built executable against the
  full catalog.
